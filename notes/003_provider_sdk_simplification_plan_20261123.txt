Provider SDK simplification and batch execution plan
===================================================

Date: 2026-11-23
Status: steps 1-2 and 4-5 complete; step 3 remains separate (NMRNet delegated); step 6 in progress

Purpose
-------

Reduce the code each provider must write to run science through the NMR API.
Simplify scientific interfaces before adding SDK abstractions around existing
protocols. Provider code should describe its science and product behavior;
provider-core should own the common execution and service lifecycle.

This note records the agreed roadmap across chefnmr2-repro,
nmr-provider-tools (including its four examples), nmrpeak-repro, nmrnet-repro,
secs-repro and magnet-deploy. Sibling paths below are inspection references,
not runtime dependencies. Recheck source and repository instructions when
starting each implementation slice.

Starting point before implementation
------------------------------------

- ChefNMR2 pins provider-core 0.7.2. Its working tree already contains an
  uncommitted batch-wire change: ElucidationBatch.requests is processed
  sequentially and ElucidationBatchResult.replies preserves entry order.
  Ordinary model exceptions become per-entry diagnostics. A lost worker or
  transport can still prevent the whole reply from arriving.
- Chef's API adapter currently submits singleton batches. Batch-shaped wire
  input does not itself enable concurrent job acquisition or batch assembly.
- ScientificCall already owns analysis/result cleanup and bounded retry for
  independent typed calls. It rejects bindings that exchange live state handles.
  Do not build a second implementation of those existing responsibilities.
- ExecutionSettings already owns host startup/retirement through
  open_contribution() and open_process_call().
- JobService currently runs one API job at a time. NMRPeak and Magnet retain
  their own service composition for multiple offerings.

End-state contract
------------------

[ ] Provider code declares scientific input/output types, loaded model setup,
    scientific operations, interpretation prompts and product result mapping.
[ ] SDK code owns admission, invocation, retry/backoff, task cancellation,
    resource settlement, API coordination and delivery lifetime.
[ ] Independent operations accept ordinary typed inputs and return ordinary
    typed outputs. No worker-state handle is required merely to connect stages.
[ ] Preparation can retain immutable data when needed. Moving large data or
    repeating expensive preparation is evaluated before removing worker-local
    state; retained state remains an explicit option where justified.
[ ] Every acquired worker, interpreter, upload and intermediate result has one
    cleanup owner. A caller timing out does not imply the resource has stopped.
[ ] A delivery or report-assembly failure does not rerun completed science.
    Transport uncertainty does not authorize replay of a possibly executed call.
[ ] Deployment configuration owns operational limits and error policies.
    Scientific code owns whether a completed result is scientifically usable.
[ ] Examples demonstrate the same supported interfaces used by real providers.
    Low-level examples remain only where they deliberately teach those APIs.

Provider-specific requirements
------------------------------

ChefNMR2
  Preserve ordered batch replies, sample budgets, seeds and per-entry failures.
  Keep model loading outside the request loop. Initially execute batch entries
  sequentially; tensor batching across molecules is outside this plan.

NMRPeak
  The present prepare/generate split retains encoded input in the worker so
  generation consumes exactly the accepted preparation. The interpreter can
  receive token-limit feedback before generation. Proposed simpler interface:
  validate(input), then predict(input), with preparation and generation inside
  predict. Measure preparation time/memory and check reproducibility under the
  same model/configuration before choosing repeated preparation. This choice
  must preserve validation feedback and the exact accepted input.

NMRNet
  Inputs may be supplied geometries or generated conformers. Preserve geometry
  order, atom correspondence, source evidence and the exact coordinates used.
  A prediction retry reuses the prepared geometry batch; it must not silently
  rerun conformer generation. Geometry parsing/generation and prediction may
  require separate worker environments and lifetimes.

SECS
  Interpretation can inspect uploaded spectra and select a representation.
  Search must consume the exact prepared spectrum and formula. Keep upload
  snapshots available until their readers stop. Compare transferring prepared
  data with retaining it in the worker; do not replace it with a path that causes
  execution to reopen changed input. Preserve the scientific distinction between
  no starting candidates and an operational failure.

Magnet
  Preserve independently configured model offerings, their input/result types,
  availability and error policies. E01 already validates and then generates from
  full typed input, without requiring a preparation handle for that handoff.
  Shared service code must support multiple offerings without making one failed
  offering unnecessarily withdraw healthy siblings.

SDK examples
  Reference-match is the existing compact independent-call example. Spectrum
  summary passes portable bytes from baseline correction to peak detection;
  its scientific dependency does not require live state handles. The NMRPeak
  mock currently demonstrates prepare/generate state custody. Dummy-provider
  demonstrates basic contribution startup and execution. Decide which examples
  teach normal usage and which intentionally teach lower-level ownership.

Implementation checklist, in priority order
-------------------------------------------

Step 1's direct-call cleanup can ship independently of its spectrum experiment.
Step 2 is investigation only; implement its selected provider boundaries after
the applicable step 3 call/recovery contract is available. Steps 4 and 5 have
their own first consumers and qualification. Step 6 is a separate capability,
not a prerequisite for releasing earlier boilerplate reductions. Completing
every provider migration is not a prerequisite for a first Chef/SDK release.

Quality criteria below apply separately to batches 1-6. They are review gates,
not a score to average: an ownership or correctness failure cannot be offset by
fewer lines or more tests. For each implementation slice, record the source
revision, applicable criteria, concrete evidence and any remaining limitation.
A criterion requiring another consumer stays pending until that consumer is
covered; a useful partial slice does not complete the whole batch. Adding these
criteria does not itself constitute a new audit of completed batch 1.

Across all batches, prefer the existing SDK authority, delete replaced paths,
and keep scientific/product decisions in the provider. A new public abstraction
must remove a demonstrated responsibility from its first consumer, not merely
rename its callback chain. Test consequential boundaries with the smallest
reproducible cases; do not require redundant assertions, arbitrary coverage/LOC
scores, or live-model runs for changes that cannot affect science. Run the
relevant maintained container lanes, review new checker findings, and retain
existing failures honestly in the SDK report. Publication and deployment are
separate gates from local implementation completion.

   Quality criteria for batch 1 — independent calls

   Q1.1 Ownership: one SDK call owns each analysis and result release; the
        enclosing host scope owns the loaded model. Chef's API controller owns
        its execution task; a standalone spectrum invocation owns its sequence.
        No provider duplicates SDK submit/wait/cancel/join/release machinery.
   Q1.2 Interface: spectrum's scientific sequence is ordinary typed calls with
        the exact corrected spectrum as downstream input. Adding another
        independent stage requires scientific code and binding/setup, not a new
        provider lifecycle state machine. Configuration is read once per startup.
        Chef batches preserve reply order/cardinality, per-entry model failures,
        and each request's sampling budget and seed.
   Q1.3 Interruption: cancelling an observer after either stage dispatch allows
        rejoining the original invocation, with one calculation per stage under
        the one-attempt policy. Closing the owner instead requests stop once and
        settles active work before its host can retire, including repeated
        cancellation of the closer. An overdue flag never means cleanup ended.
   Q1.4 Failure: failed encoding/cleanup prevents downstream dispatch; uncertain
        submission or failed publication never reruns science. Bounded peak
        admission retry preserves corrected input without repeating baseline.
        Independent body/cleanup failures survive. Changed behavior is explicit
        in the consumer contract, not hidden by deleting an old assertion.
   Evidence: focused interruption/rejoin and close tests at both stages; exact
        intermediate-input comparison; no-replay/failure cases; installed
        thread/process example runs and Chef's existing call-ownership tests.
        Include mixed-success Chef batches and sampling-parameter propagation.
        Confirm obsolete workflow code and its callers are gone.
   Stop condition: any unowned task/resource, hidden replay, or retained caller
        cleanup wrapper without a distinct obligation leaves this batch open.

2. Investigate preparation boundaries before changing their implementation

   Decision rule (user clarification, 2026-11-23): existing behavior is evidence,
   not automatically a compatibility requirement. Preserve behavior when it
   serves scientific identity, an intentional product policy, or a concrete
   ownership/recovery obligation. Treat opaque handles, repeated validation,
   custom wire exchanges and provider lifecycle wrappers as replaceable means.
   A model-required representation stays; an admission rule that accepts input
   the model cannot consume is a defect, not a contract to reproduce.

   For each provider, explicitly select what to keep, simplify or remove, with
   the reason and the resulting acceptance cases. Compare the facts that matter,
   not incidental object identity or every legacy intermediate. Measurements
   should resolve a consequential choice; do not expand them merely to reproduce
   every historical path. Changed intentional behavior must be documented, not
   concealed by removing a test. Implement selected changes in later batches.

   [x] Evaluate NMRPeak's validate/predict boundary using captured input bytes
       and the same pinned model, tokenizer, dictionary and encoding settings.
       Compare token count and encoded source tensor values/shape/dtype, including
       special tokens and padding, between validation and prediction. Exercise
       corrected proposals and token-limit rejection as well as valid inputs.
       Inspect preparation for mutable/random inputs; repeated matching samples
       alone do not prove determinism. If identity cannot be established, retain
       prepared data. Separately record preparation time and peak memory against
       prediction cost before choosing repetition versus retention.
   [x] Record the selected NMRPeak boundary and its necessary SDK capabilities;
       implement it in real NMRPeak and the mock under step 3. Do not require
       bitwise equality of stochastic candidates to prove prepared-input identity.
   [x] Specify NMRNet's prepared geometry collection as the input to prediction.
       Record exact prediction request bytes, order, atom/source correspondence
       and admitted runtime identity. Replacement retries reuse those bytes;
       require a check that conformer generation is not invoked again. Custom
       invocation migration waits for step 3's complete recovery contract.
   [x] Determine SECS prepared-data size, preparation cost and source ownership.
       Choose an ordinary immutable input or justified worker-local retention.
       Compare spectrum values/shape/dtype, canonical formula, representation
       metadata and source snapshot identities. Exercise source replacement or
       deletion after capture: execution must use admitted data or reject before
       science, never read replacement bytes. Verify source release follows
       confirmed reader shutdown, including preparation failure/cancellation.
   [x] Specify Magnet's typed validation/generation contract for the later
       shared transport/lifecycle migration under step 3. Compare model inputs,
       result schema/context and public outcome mapping at that boundary; test
       eligible model failure, ineligible failure and lost outcome separately.
   [x] If live state remains necessary, identify the missing SDK analysis/
       submission guarantees for that concrete consumer. Do not propose a general
       workflow engine merely to reproduce today's application state machines.

   Quality criteria for batch 2 — preparation decisions

   Q2.1 Scientific identity: each proposed boundary names the exact accepted
        input and everything that can change its preparation. NMRPeak includes
        model/tokenizer/dictionary settings and encoded tensors; NMRNet includes
        geometry order, coordinates and atom/source correspondence; SECS includes
        captured spectrum bytes, formula and representation; Magnet includes
        typed validation inputs, model identity and result semantics.
   Q2.2 Ownership: for each retained object, identify who owns it, who can still
        read it, and when it can be released. A mutable path is not a substitute
        for captured data. Retain worker state when identity or resource cost
        requires it; removing every handle is not a quality target.
   Q2.3 Cost: measure representative preparation time, peak memory and transferable
        data size, alongside prediction cost, under recorded input/model/runtime
        settings. Use those measurements and deployment limits to justify
        recomputation versus transfer versus retention. State uncertainty and
        supported input sizes; do not invent a universal speed threshold.
   Q2.4 Decision: record the selected interface for each provider, rejected
        alternatives and their concrete costs, necessary SDK capabilities, and
        migration acceptance cases. Source inspection must address randomness
        and mutable inputs; a few matching runs alone do not prove determinism.
   Evidence: captured-input comparisons, corrected/rejected proposal cases,
        source replacement/deletion after capture, cancellation while readers
        remain active, and reproducible measurements. For stochastic science,
        compare prepared inputs and declared behavior, not random outputs bitwise.
   Stop condition: an unproven input identity or unmeasured cost needed for a
        decision blocks that provider's migration. Batch 2 completes with
        evidence-backed decisions for the listed providers, not migrated code;
        the selected implementations belong to later batches.

3. Complete common call ownership and configurable error handling

   [ ] Extend existing ErrorPolicy/ScientificCall where consumers expose gaps:
       immediate raise, bounded attempts, backoff and explicit retry eligibility.
   [ ] Distinguish confirmed non-admission, confirmed calculation failure,
       unknown outcome and cleanup failure using existing SDK facts.
   [ ] Recheck job permission before each attempt and preserve original input.
       Worker replacement, when allowed, follows confirmed old-worker retirement.
   [ ] Use NMRNet's _retry_prediction as the first replacement-retry contract.
       Define the integration against its real allocator/worker before exposing
       a generic API: provider supplies the captured input, scientific prepare/
       execute methods, eligible model-failure category and runtime requirements;
       SDK owns configured acquisition, acquired-worker custody, retirement and
       the overall recovery budget. Whether the existing host factory suffices
       or needs an adapter is a prototype decision, not a promised capability.
       Do not move an allocator/retry callback chain wholesale into a new wrapper.
   [ ] Before migrating NMRNet/Magnet retry code, support the complete original
       recovery budget across stop, replacement, preparation and redispatch.
       SDK owns this ordering and preservation of the first failure alongside
       later independent failures. Provider supplies scientific retry eligibility
       and the admitted runtime/model identity; SDK enforces that replacement
       meets it before redispatch. Do not broaden NMRNet's exact ModelCallFailed
       eligibility into retrying any exception or worker crash.
   [ ] Keep product-specific scientific rejection/result mapping in the provider;
       providers must not reconstruct generic SDK failure classifications.
   [ ] For a partially executed batch, never replay successful entries as an
       incidental consequence of retrying another entry or losing the reply.
   [ ] Migrate each step 2 consumer only once its input-identity, ownership and
       recovery requirements are demonstrated by the SDK/consumer slice. Apply
       that same interface to its example and remove superseded plumbing.

   Quality criteria for batch 3 — recovery ownership

   Q3.1 Authority: the SDK owns attempts, backoff, cancellation, acquisition and
        retirement. Deployment selects limits; the provider supplies scientific
        retry eligibility and required model/runtime identity. Consumers do not
        recreate SDK failure classifications or hide their old loops in callbacks.
   Q3.2 Replay: non-admission, confirmed calculation failure, uncertain outcome
        and cleanup failure have distinct actions based on SDK evidence. Only
        explicitly eligible, settled failures permit another calculation. Never
        replay success to recover delivery, or infer an unexecuted batch suffix.
   Q3.3 Bounds: define maximum attempts, backoff cap and recovery-budget scope.
        Time spent stopping, replacing and preparing consumes that same recovery
        budget; replacement cannot reset it. Budget exhaustion forbids new work
        but does not abandon mandatory cleanup or claim a worker has stopped.
   Q3.4 Ordering: before redispatch, confirm old-worker retirement, replacement
        identity, unchanged prepared input and current job permission. Preserve
        the original failure alongside independent replacement/cleanup failures.
        A lost reply remains uncertain even when replacement is available.
   Evidence: NMRNet allocator/worker cases covering eligible and ineligible
        failure, exhausted budget, revocation during backoff, failed retirement,
        incompatible replacement and lost outcome. Verify ordered effect traces
        and identical prediction inputs; conformer generation must not recur.
        Exercise the same supported interface in the migrated real consumers and
        their examples; retain product-specific rejection mapping tests.
   Stop condition: broader retry eligibility, a refreshed budget, replacement
        before retirement, or application-owned generic recovery keeps the
        affected migration incomplete. One consumer does not certify all others.

4. Consolidate interpreter construction and lifecycle

   [x] Move endpoint/key/CA construction and shared retry-service setup into the
       SDK, consuming captured configuration material where callers already own
       immutable snapshots. Avoid reopening files behind those callers' backs.
   [x] Let the SDK own each conversation and its cancellation/cleanup.
   [x] Preserve provider-owned prompts, source selection, scientific validation
       feedback and decisions about public versus protected diagnostics.
   [x] Support both typed proposal decoding (Chef) and scientific preparation
       feedback (NMRPeak/SECS); reuse existing Interpreter/PreparationTool APIs.

   Quality criteria for batch 4 — interpreter setup and lifetime

   Q4.1 Separation: the SDK constructs endpoints, credential/CA transport and
        shared retry services, and settles each conversation. Provider code owns
        source selection, scientific tools, validation feedback and public versus
        protected diagnostics. Prompts and tool prose remain provider resource
        files; the SDK must not embed Chef-specific instructions or outcomes.
   Q4.2 Configuration: consume the caller's captured configuration/material
        consistently; do not reopen mutable files behind a snapshot owner. Honor
        explicit endpoint, proxy, TLS and budget settings without a silent fallback.
        Shared endpoint services retain retry state only; conversations own model I/O.
   Q4.3 Scientific behavior: both typed proposals (Chef) and scientific
        preparation feedback (NMRPeak/SECS) use the same supported SDK setup.
        Rejected proposals retain the conversation for correction without
        authorizing prediction. Malformed structured input does not enter prose
        interpretation; unsupported attachments are not silently ignored.
   Q4.4 Cancellation: revocation during a tool call or retry prevents later
        scientific effects. Conversation tasks and any preparation readers
        settle before their source snapshots, uploads or shared services close.
        Endpoint failure is not presented as scientific rejection.
   Evidence: migrate a typed-proposal consumer and a preparation-feedback
        consumer; exercise correction, malformed structured input, endpoint
        failure/backoff, cancellation during a tool call and shutdown. Verify
        selected transport settings and captured-material ownership. Reuse
        existing SDK protocol tests rather than copying their internals.
   Stop condition: providers still construct transport/lifetime machinery, the
        SDK decides scientific validity, or a generic setup bypasses a consumer's
        source/feedback requirements. More constructors alone are not completion.

5. Consolidate service composition and multiple offerings

   [x] Move repeated API/delivery factories, proxy configuration, signal setup
       and process-lifetime ownership behind supported SDK setup APIs.
   [x] Extend service composition to independently configured offerings, with
       per-offering readiness, worker exit observation and capacity.
       Separate invalid deployment configuration (reject before startup effects)
       from a valid offering whose worker fails to load. Partial activation is
       a target capability, not a claim about current Magnet behavior: Magnet
       validates its configured lane inventory and builds a complete Hello
       snapshot. Before migration, qualify how the API represents an admitted
       subset and subsequent withdrawal/recovery without changing offering
       identity. Select all-or-nothing versus partial startup explicitly for a
       deployment; preserve its existing behavior until that choice is made.
   [x] Preserve retained Attempt and delivery obligations during shutdown.
       Removing phase flags requires identifying the SDK owner replacing them.
   [x] Migrate NMRPeak/Magnet service composition only after those behaviors are
       represented; a single-host JobService wrapper is not sufficient.

   Quality criteria for batch 5 — service composition

   Q5.1 Composition: SDK setup owns repeated API/delivery factories, proxy setup,
        signal handling and process lifetime. Providers declare their offerings,
        host associations and product mappings. Adding or removing a supported
        offering changes that declaration, not duplicated service loops or a
        second manually synchronized offering inventory.
   Q5.2 Startup: invalid deployment configuration fails before startup effects.
        A configured worker's load failure follows an explicit all-or-nothing or
        partial-startup policy. Partial startup requires API evidence that the
        advertised subset and later withdrawal/recovery preserve offering identity;
        do not infer support from independently running workers alone.
        Readiness requires usable shared prerequisites and all required offerings
        under all-or-nothing policy, or at least one usable offering under partial
        policy. A started process alone is insufficient.
   Q5.3 Failure scope: worker exit withdraws every offering on that host and
        preserves affected Attempt evidence. Independent healthy hosts remain
        usable under partial policy. Shared API/identity failure pauses admission
        according to shared recovery policy without inventing scientific failures.
   Q5.4 Shutdown: stop admission, settle original execution/readers, and preserve
        or settle selected result/delivery obligations before releasing their
        resources. Delivery backpressure or cancellation cannot drop an accepted
        report or rerun science. Observe the existing delivery reconciliation
        contract rather than claiming external acceptance from a local write.
   Evidence: use real multi-offering consumer composition, including multiple
        offerings sharing a host and offerings on separate hosts. Test load
        failure, worker exit, shared API failure and shutdown during delivery;
        inspect effective Hello/availability and retained Attempt state. Qualify
        partial publication against the API contract before enabling that policy.
        Update examples to the same setup interface; remove old composition paths.
   Stop condition: a single-host wrapper presented as multi-offering support,
        advertising a failed offering, withdrawing unrelated healthy offerings
        under partial policy, or losing outstanding delivery obligations.

6. Add bounded concurrent acquisition and batch assembly

   [ ] Separate fetching/claiming and preparation from worker execution, using
       explicit bounds for active Attempts, concurrent preparations, queued input
       bytes and retained result/delivery bytes. Stop acquisition at capacity;
       slow delivery may eventually apply backpressure, but need not immediately
       serialize otherwise available work. Reuse SDK Attempt claims and limits.
   [ ] Configure maximum batch size and collection delay. Group only requests
       compatible with the selected worker/model and execution settings.
   [ ] Retain an explicit association between each batch entry and its API job.
       The SDK owns scheduling/routing; Chef owns its scientific batch schema.
       An SDK dispatcher owns the one batch invocation, its original task, and
       the ordered entry-to-Attempt mapping through result extraction/cleanup.
       An Attempt owns its input evidence, permitted outcome and delivery, not
       the shared worker. Its waiter cannot cancel or retire a sibling's work.
       Use existing Attempt records for per-job evidence; do not add a second
       durable batch ledger. Retain the mapping until each entry is transferred
       to its Attempt owner or settled without publication.
   [ ] Supply provider packing/unpacking at the typed batch boundary. Reject a
       reply with wrong cardinality or invalid entries before routing any result.
       Correlation follows the dispatch snapshot, not equality of input values.
   [ ] Check each job's permission before admission and immediately before batch
       dispatch; remove cancelled queued entries. After dispatch, cancellation
       revokes that job's publication authority but cannot independently stop a
       sequential worker entry with today's whole-batch protocol. Proposed first
       behavior: finish the already-dispatched batch, retain cancelled entries
       until their work settles, and suppress their success publication. An
       entry revoked before its turn may still execute; today's protocol cannot
       remove it from that dispatched batch.
       Verify this against the SDK/API cancellation contract before enabling
       cross-job batching. If it requires per-entry stopping, implement that
       protocol first; do not silently weaken cancellation or enable batching.
   [ ] Only the dispatcher requests whole-batch retirement, for shared failure,
       global stop, or cancellation of all participants. A cancelled Attempt's
       retirement joins settlement of its participation instead of declaring its
       work stopped or retiring a host still used by siblings.
   [ ] Apply the initial retry/outcome table below. The existing wire returns one
       complete reply; it has no streaming progress or trustworthy partial-prefix
       completion record. Partial-result recovery and per-entry model retries
       are not required for the first batching version.
   [ ] Keep worker execution sequential initially. Parallel preparation and
       acquisition do not imply simultaneous model calls or tensor batching.

   Quality criteria for batch 6 — concurrent jobs and batch assembly

   Q6.1 Bounded progress: acquisition/preparation can advance while science or
        delivery is waiting, when capacity exists. Set explicit limits for active
        Attempts, concurrent preparation, queued input bytes and retained
        result/delivery bytes. Account for in-flight reservations before taking
        more work; at capacity stop admission rather than spawning unbounded
        waiting tasks. Size or collection deadline triggers batch dispatch.
   Q6.2 Routing: one dispatcher owns each invocation and its immutable ordered
        entry-to-Attempt mapping. Group only compatible worker/model/execution
        settings; provider packing/unpacking owns the scientific schema. Check
        the whole reply's cardinality and entry validity before routing any
        result. Equal scientific inputs never substitute for job identity.
   Q6.3 Cancellation: remove revoked jobs before dispatch and check permission
        again immediately before it. After dispatch, one job cannot cancel or
        retire sibling work. Keep its participation until settlement and suppress
        unauthorized publication, preserving already selected delivery semantics.
        First prove this is permitted by the API cancellation contract; if it
        requires stopping individual entries, implement that protocol before
        enabling shared batches. Document that current sequential entries may
        still run after their participant is revoked.
   Q6.4 Failure: preserve each confirmed entry outcome, but treat malformed or
        lost whole replies as unresolved without guessed progress or replay.
        Only the dispatcher retires shared work. Shutdown or cancellation of all
        participants joins the shared invocation before releasing resources.
        No second durable batch ledger or per-job host-retirement wrapper appears.
   Evidence: controlled blocking points show a second job acquired/prepared while
        the first is executing, and show admission stopping at each configured
        limit. Check size/deadline dispatch, incompatible groups, identical inputs
        from different jobs, revocation before/after dispatch, sibling delivery
        failure, worker exit after one entry, malformed replies and shutdown.
        Assert routed identities, bounded live counts/bytes and calculation counts;
        a throughput number or sleeps alone do not establish these properties.
   Stop condition: serial acquisition at free capacity, unbounded retained work,
        premature participant release, cross-job cancellation, misrouting or
        replay after uncertainty. Tensor batching and parallel model execution
        are not required; the first worker may process entries sequentially.
