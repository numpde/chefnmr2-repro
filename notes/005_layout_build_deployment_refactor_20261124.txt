ChefNMR2 layout, build and deployment refactor
============================================

Date: 2026-11-24
Status: implementation underway; batch 1 committed as 66e0c54, batch 2 pending
Baseline: 222c7b8; ChefNMR2 submodule 9922b6c571428757c37f127225a62f2070d6ddc0

Completion contract
-------------------

- One provider image serves CPU and GPU deployments. One worker Dockerfile and
  one SDK contribution implement both worker variants. The SDK remains the
  runner/process owner; do not reintroduce worker.py or a custom supervisor.
- model/binding.py owns the scientific operation and lifecycle; model/wire.py
  owns its request/result types. Both images consume the same declaration.
  Scientific imports remain lazy so the provider needs no Torch installation.
- docker-bake.hcl owns image targets, pinned bases, target platforms and named
  build contexts. Each builds/<profile>/requirements.in owns direct dependency
  intent; its generated requirements.lock selects the complete target-specific
  artifact closure. builds/sdk.constraints.txt selects one SDK release.
- Compose owns runtime topology and containment. Deployment overlays own host
  mounts, resource settings, selected image digests and GPU device grants.
  provider.toml owns SDK/scientific/API settings. No custom config merger.
  Each deployment's compose.yaml supports worker/manual operation alone;
  provider.yaml adds API-only grants and configuration when API service is used.
- Qualification runs the actual worker/provider images with the selected
  deployment configuration and separate runner state. Credentials and API
  connectivity are unnecessary for manual model qualification.
- The existing CPU environment and behavior survive the move. CUDA is a
  separately qualified environment; it cannot silently replace CPU packages or
  fall back to CPU inference.
- Old executable paths, duplicate configs and unused commands disappear when
  their consumers move. Historical notes keep their original paths as evidence.

Commit and review discipline
----------------------------

Each numbered batch has a coherent commit boundary; split further only where
each commit has a working consumer and removes the authority it replaces.
Update this checklist with evidence and material deviations as work completes.
Keep relocation changes distinct from dependency/environment changes so reviewers
can identify the source of a regression. Do not mix the unrelated ProArt note
into these commits. A blocked CUDA batch must remain visibly incomplete.

Review ordinary next changes before declaring completion:
- SDK bump: change its common selection and regenerate affected target locks;
  no Dockerfile or Python version literal needs editing for an SDK-only change.
- Python/CUDA change: change the selected base/profile inputs, regenerate the
  appropriate lock and requalify; the provider need not follow worker ABI changes.
- Second GPU deployment: add its concrete overlay/TOML, without copying model
  code or creating another provider image.
- Interpreter prompt edit: rebuild provider only; worker lock/image stays valid.
- Interrupted build/qualification: project-owned staging and runtime scratch
  clean up; shared caches, weights, credentials and other providers remain intact.

Joint file-placement criteria — candidate v14

Purpose and scope
Decide every repository-owned file's necessity and location in chefnmr2-repro
and moldetr-repro before approving a tree. Cover authored code, Make recipes,
Docker/build/runtime configuration, reviewed or generated locks, tests and their
fixtures, documentation, and generated artifact families. Include untracked work.
Treat each upstream submodule as an externally owned boundary, not permission to
rearrange its contents. Preserve user-owned IDE configuration, credentials,
caches and retained experiment/recovery evidence. Inventory their ownership and
lifetime without treating inventory as deletion or transfer authorization.

No existing path, proposed directory map, current investment, genericness or
same filename is evidence of correct ownership. No bucket named common/shared.
No placement is preapproved, including model/checkpoints.py or test directories.
The criteria govern choices; a directory map is a result of applying them.

Required record
For EACH owned file, record its responsibility and owning decision/change
trigger; actual producer and build/operator/runtime/test consumers; whether it
is authority, projection or evidence; why a separate file and this location;
serious adjacent alternatives including merge/delete and their consequence;
effective input/access grants; lifetime/cleanup/recovery owner; mirror status;
relevant precedent comparison; and evidence supporting the decision. Consumers
include human readers/reviewers and tool discovery, not only runtime callers. Inspect distinct authored blocks when a
file may mix responsibilities. A family-level rule may supply repeated facts,
but each file must be named and checked for exceptions. Record unknowns; do not
turn the record into another runtime inventory or source of configuration.

C1 — Necessity and coherent granularity
Must be true: every file and meaningful block serves a current requirement or
an explicit supported contract. Separation follows an independently changing,
operated, versioned or tool-discovered boundary, or a distinct semantic contract
whose separation demonstrably improves comprehension or change safety compared
with merging it. For a disputed semantic split, compare both arrangements under the same
supported change; an assertion that one is clearer is insufficient. Consolidation
and deletion are
serious alternatives. Trace each requirement to an independently stated user
outcome, supported workflow/contract, or demonstrated failure; a newly invented
caller or feature cannot justify itself. Compare alternatives by how they satisfy
that requirement, including dropping an unsupported feature. Count avoidable
coordination as extra owners, edit sites or release steps for one supported
change. Both excessive fragmentation and mixed responsibility
must be assessed; neither fewer nor more files is a quality proxy.
Counterexample: a help-printing wrapper has a real caller but owns no decision;
or one operator script hides unrelated policies behind a broad module label.
Decisive evidence: actual call sites/tool requirements, responsibility and change
triggers, consequences of removal/merge, and the smallest coherent alternative.
Mandatory failure: no necessary consumer/contract, or separation justified only
by genericness, existing placement, test count, or symmetry.

C2 — Semantic ownership, placement and dependency direction
Must be true: the path expresses the decision owner, established independently
of who currently executes or calls the file. Distinguish the owner of a behavior's
contract from the physical file, image/build and execution owners where they
differ. Where a contract has inseparable joint owners, name their respective
decisions and the composition/interface owner rather than inventing a universal
single-owner tie-break. Name the controlled inputs, who changes them, and source
evidence showing which component actually determines the behavior. Compare the nearest viable owners and locations, including a
package/tool owner where relevant. A reusable mechanism need not belong beside
one current caller, and reuse alone does not establish a package boundary.
Counterexample: putting a loader in a model directory solely because a model
calls it; or moving a copied utility to a vague generic bucket.
Decisive evidence: input-to-effect dependency graph; a representative supported
change and, where an independent adjacent change exists, one plausible change
that should not propagate to this owner. Do not invent independence or reject
legitimate coordinated changes merely to supply an example;
tool discovery/import/build-context constraints, and rejected alternatives with
specific costs. For documentation, historical evidence and other non-executable
files, establish the content/curation/publication owner plus the reader,
discovery and retention contract; do not invent a runtime decision owner or
caller. Tests and configuration similarly use their actual kind of contract.
Mandatory failure: ownership is inferred from the current path/caller/executor,
or the proposed move creates an unexplained reverse dependency or owner.

C3 — Authority, derivation and provenance
Must be true: each independently edited fact has one identified authority,
including facts carried inline as constants or choices rather than separate files.
State the fact at its authority layer: an upstream identity, a reviewed expected
result and a measured artifact generation are distinct facts. A local projection
of external authority is not automatically a competing authority.
Every projection/reference/evidence file has its authoritative inputs, producer,
regeneration or review owner, consumer and staleness behavior. Exact output pins
and checked-in generated references require a separately established user,
scientific or operational acceptance requirement which they materially verify.
A checker or target created solely to read a file does not establish that
requirement. Bind an approved expected reference to its accepted generation,
inputs (including output-affecting dependencies, toolchain and runtime facts)
and transformation version so later consumers can detect a stale or mismatched
reference. Neither ban nor retain a file merely because it is generated.
Counterexample: a target list, precision menu and implementation all maintain the
same choices; or an approved reference is deleted just because it is derived.
Decisive evidence: trace a real fact through its update workflow; identify every
manual edit and what detects stale or mixed versions. Compare deriving, keeping
or removing the file without adding a second policy carrier.
Mandatory failure: mirrored editable authority, undocumented generation, or an
output lock/reference with no consumer whose acceptance need is independently
established.

C4 — Effective authority and artifact lifetime
Must be true: placement preserves the actual execution and data boundaries:
inputs/environment, build contexts, engine/filesystem/network/device grants,
secrets and mutable storage. Every generated family has a producer, ordinary
consumer, retention reason and owner of applicable cleanup/recovery duties.
Name which duties do not apply and why. For each persistent or retained family,
record its actual storage destination, the boundary that makes it persist
(checkout, engine volume, external cache or another owner), and the operation or
owner authorized to retire it. Retained evidence and reusable inputs are distinct
from disposable work.
Counterexample: a neatly placed Compose file inherits an ambient engine or
exposes the whole checkout; or partial receipts/staging files have no retry or
cleanup owner. Conversely, unneeded copying or deletion can violate ownership.
Decisive evidence: effective invocations/mounts/interpolation, resulting artifacts
and representative lifecycle behavior. Require interruption/retry evidence when
interruption can affect persistent or retained state, publication correctness,
recovery or resumption; otherwise state why that failure proof does not apply.
Disposable scratch still needs ordinary cleanup and safe-discard ownership, but
its possible residue alone does not require a dedicated interruption test. When publication/migration correctness
or recovery depends on multiple durable states or a retry boundary, show the
state before/after each consequential mutation, relevant interruption points,
what retry uses, and which temporary state may be discarded. A single atomic
output without recovery dependencies needs only its ordinary before/after
contract, not a separate durability analysis for every write. Assess whether
supported invocations can overlap; where they can, show safe reader/writer and
writer/writer behavior or an enforced exclusion, even if concurrency was not
advertised. Identify the coordinated resource by its actual backing storage,
not only an engine/context alias: different engines may share backing storage,
while different aliases may refer to one server. The exclusion/proof must cover
the same mutated resource across supported paths. Distinguish managed writes
from external mutation. Preservation means retaining required recovery/evidence, not every
transient file. Identify authority limits and uninspected hosts without inventing
new approval requirements.
Mandatory failure: unowned effective grants, generated residue or recovery state;
or a move/cleanup that exceeds the user's authorized scope.

C5 — Mirrored structure with explicit divergence and drift control
Must be true: equivalent responsibilities have equivalent structure and naming
across the repos where doing so improves understanding and maintenance. Each
difference names its concrete requirement. Identical code copies have an update
owner and an explicit parity-verification workflow. State what parity means
for each mapped responsibility: identical mechanism, equivalent contract or
matching structure. Name the check, its scope, permitted differences and their
requirement, its change/review trigger, and what a mismatch blocks. This can be
a coordinated review procedure; it need not introduce a cross-checkout runtime
or CI dependency. Copied files do not become a single package or authority by
assertion. A new dependency/package must earn
its own release, installation and failure lifecycle. Genuinely independent
contracts or change cadences may justify divergence when demonstrated by their
requirements and update effects; mere ownership by different repos does not.
Counterexample: matching empty folders/wrappers without consumers; or identical
checkpoint modules silently drifting after the next fix.
Decisive evidence: side-by-side responsibility map, justified per-file differences,
the actual current parity result (or justified non-applicability), and a workable
next-update/parity check that preserves independent checkouts. A future process
alone does not prove the current copies or contracts are aligned.
Mandatory failure: cosmetic symmetry adds machinery, unexplained divergence,
or a claim of one implementation without a synchronization responsibility.

C6 — End-to-end purpose, evolution and proof
Must be true: the resulting placement supports the requested behavior through
the real operator/build/producer/consumer path. Distinguish production, test-only,
explicitly requested future interfaces and unreachable code. List bypasses and
whether they leave the requested outcome incomplete. An interface without an
actual intended consumer can be retained only for an explicit requested or
supported contract; its tests prove that contract, not runtime enforcement. If
the requested behavior needs a consumer that does not exist or cannot be changed
within scope, record the unmet acceptance condition and required owner/action.
Do not invent a runner or silently redefine the request as a future foundation.
Evaluate the next ordinary
change, removal, clean invocation and consequential failure, not only today's
passing snapshot. Proof must use the reviewed files/artifacts and respect the
no-large-download, no-unrequested-upstream-edit and selected-checkpoint limits.
Counterexample: a receipt helper passes tests while the intended loader bypasses
it; category directories exist but maintained discovery skips their tests; or a
routine new profile requires editing a hidden parallel inventory.
